# ref-21 — 上下文工程协议（coding-agent-os §7/§16 吸收）

> 吸收来源：`coding-agent-os-architecture.md` §7 Context Engineering、§16 Cost/Token Optimization、§28.6 Token 优化策略摘要。
> 落地形态：**协议文档**（本节）+ SKILL.md §7（稳定前缀，G5）升级为"检索协议 + 前缀"双层。

## 1. 与 SKILL §7 的关系

SKILL §7 管**静态前缀**（可缓存、字节稳定，G5）；本节管**动态检索**（每次调用的最小充分上下文，G1）。两者合并为完整上下文流水线：

```
固定前缀（system + 不变任务指令 + 技能说明）→ 动态检索物（本节）→ volatile 用户输入/检索结果（最后）
```

## 2. 检索顺序（每次调用，6 步）

1. **任务切片**：只取当前状态（ref-20）相关的任务片段，不带全历史；
2. **符号 1-hop**：AST 签名 / 调用者 / 被调者 / 测试文件（图谱优先于全文，§6 minimal-need）；
3. **语义 top-k**：相似检索，去重（同源/同签名合并）；
4. **排序**：recency > 图距 > 词面重合 > 先验失败（error-signatures 命中前置）；
5. **按类预算**（见 §3）：丢弃最低排序项——**宁可少给，不可给错序**；
6. **适配器格式化**：按模型工具协议（JSON schema vs XML tool template，ref-02）组织成模型最易消费的形状。

## 3. 按类预算（§16 吸收）

| 类 | 适用 | 预算（token 量级） | 纪律 |
|---|---|---|---|
| A（紧） | 分类/抽取/格式化（T2） | 几百 | 只给样本格式 + 本次输入 |
| B（中） | 常规代码/摘要（T1） | 1-8K | 任务切片 + 符号 1-hop + top-k 语义 |
| C（松） | T0 架构/长文档分析（1M ctx） | 16K+ 整文档 | 整文档注入 + 节引用，cite sections |

**禁项**：中文件截断（宁整块给或整块不给）；重复给同内容不同格式；把整个 repo 树塞进单次调用。

### 3.1 分类预算明细（R-6，吸收 ResourceOS §14.3 + §32.3）

SKILL §7 给**上限表**（一屏可查），本节给**压缩规则**（超限怎么办）。A/B/C 按任务类型分档，本表按内容类别分档 —— 两者相乘即用：先定档再按类分配。

| 类 | 压缩顺序（超限即执行，自上而下） |
|---|---|
| 活动资源 L3（refs 全文） | 全文 → 摘要+指针行 → 只留标题行（下次调用再取） |
| 前序结果 / 检索 hits | 逐条原文 → 去重后仅结论行 → 仅保留与当前子任务相关条目 |
| memory（4 层 JSON + 宿主记忆） | 全量命中 → 只留命中条目 → 只留 conventions/solutions 两层 |
| task（不变指令） | 下沉 refs，SKILL 只留指针行 |

**不参与压缩**：`system`（固定前缀 / 缓存区，动它等于放弃 cache 命中）。

**reasoning 硬底线（协议级，不可协商）**：输入类预算再紧张也不得挤占输出推理空间 —— 压缩只对输入类生效；`max_tokens` 不得因注入而低于任务档位（SKILL §2.2）所需。二者冲突时**先砍输入**，因为输出被截断 = 本轮推理白费，输入被压缩 = 可再检索。

**参考锚点**：ResourceOS §31 给的全链执行示例为 10–20K token（其规模 10³–10⁶ 资源下测出）。SDK 侧资源量约 50 个，实测全链远低于此 —— 该数字只作**量级校验**：若某条任务链估算远超 20K，先怀疑注入面失控，而不是继续加料。

## 4. 默认排除清单（每次调用先排除，再决定给什么）

- 构建产物、node_modules、dist、缓存目录；
- 与当前状态无关的历史 diff；
- 已由工具结果覆盖的上下文（verify-runner 已给的 pass/fail 事实，不重复叙述）；
- 用户没要求展示的日志全文（bounded tail，G1）。

## 5. 缓存策略（G5 强化）

- 稳定 80% 放前缀内，易变 20%（检索结果、时间戳）放尾部；
- 检索物按版本标记（`<source src="...">`），20% 变化时只推尾部；
- cache hit <60% 视为前缀构建失败（token-meter 指标，ref-05）。

## 6. 压缩时机（与 ref-20 黑板联动）

状态转移 / 黑板 recent_actions 超阈（cap 8）→ 用 Class-A 模型把旧上下文压缩成任务记忆条目（事实/决策/待办），进 `.workbuddy/tasks/<id>.json` 的 blackboard.facts——压缩是**写记忆**不是丢信息。

### 6.1 测试生成材料的选择策略（v2.9.0 T-28，verification-kernel §B.12/§B.13 协议化）

- **Property-based testing**：仅对纯函数 + 可推断不变量（round-trip / idempotence / monotonicity）值得做；I/O 密集或有副作用代码跳过。技能层脚本以确定性单例为主，协议上保留、不落地工具（ALIGNMENT 排除总表）。
- **Mutation testing**：kill-rate 只对关键路径有信号；全量突变在低配机不可承受。协议：仅当任务声明"关键路径"且 CI 有预算时按需（如 `mutmut --paths-to-mutate <单文件>`），默认不做。

## 7. 溯源台账（v2.8.0 T-13，AgentOS #2 吸收）

检索所得材料不是"进上下文就完"——每条外部材料带三元素记录，过期自动降权：

```text
{source: "<来源（URL/文件路径/文档节）>", fetched_at: "<时间戳>", cell: "<任务类别>"}
```

- **注入时**：材料块用 `<source src="...">` 标记（§5.2 grounding 的载体），来源+时间戳随块走；
- **使用时**：输出引用必须能回指台账条目（`[n]` 编号）——无来源的材料不得作为结论依据；
- **过期驱逐**：`fetched_at` 距今 > 30 天的材料降权使用，引用前必须重检一次（上游版本漂移是常态，§8）；
- **台账载体**：轻量任务直接写进当轮上下文即可；跨会话复用的进 blackboard.facts（ref-20 §5），不新建存储。

## 8. 排除项

不落地：嵌入向量服务（结构化匹配优先；本地 embedding 资产可另接为"语义 top-k"后端）、RAG 框架、上下文压缩模型常驻。
