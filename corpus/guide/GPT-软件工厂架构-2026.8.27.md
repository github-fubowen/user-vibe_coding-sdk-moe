如果你说的“高度自动化的软件生产流水线”不是单纯 CI/CD，而是：

> 从需求 → 任务拆解 → 设计 → 编码 → 测试 → Review → 修复 → PR → 合并 → 部署 → 监控 → Issue 回流 → 再次修复

那么到 2026 年，更合理的架构已经不是传统的：

```text
Git → CI → CD
```

而是：

```text
Product / Issue
      ↓
AI Orchestrator
      ↓
Agent Workspace
      ↓
Explore → Plan → Code
      ↓
Build / Test / Review
      ↓
PR
      ↓
CI
      ↓
Deploy
      ↓
Observe
      ↓
Incident / Issue
      └──────────────→ Agent
```

OpenAI 现在公开的 Codex 工作流已经明显往“issue → agent → sandbox → tested code → review/PR → background tasks”方向发展；Anthropic 则重点发展 subagents、hooks、MCP、长任务 harness 和安全隔离。([OpenAI][1])

我会把现代软件生产流水线分成 9 层。

---

# 1. 最顶层：Software Factory Control Plane

先不要从“哪个框架写 Agent”开始，而是先建立控制面：

```text
                    SOFTWARE FACTORY
                           │
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
   Product Plane      Engineering Plane    Runtime Plane
        │                  │                  │
   Requirements        Coding Agents       Deployments
   Issues              CI/CD              Observability
   Roadmap             Review             Incidents
```

核心对象不是 Conversation，而是：

```text
Work Item
```

例如：

```json
{
  "id": "TASK-1842",
  "type": "bug",
  "repository": "payment-service",
  "priority": "high",
  "status": "implementing",
  "acceptanceCriteria": [],
  "agent": "coder-01",
  "workspace": "sandbox-1842",
  "branch": "agent/TASK-1842"
}
```

这会让整个生产流水线从“聊天”变成“任务驱动系统”。

OpenAI 公开的 Symphony 思路非常值得注意：它直接把项目管理系统的任务板作为 Coding Agent 的 control plane，让 Agent 根据任务状态自动领取、执行任务，而不是每次靠人手工启动。([OpenAI][2])

# 2. Requirement → Specification

第一层 AI 不应该直接写代码。

应该：

```text
Issue
 ↓
Requirement Agent
 ↓
Specification
 ↓
Acceptance Criteria
 ↓
Implementation Plan
```

例如：

```text
用户：
“支付接口偶尔 500”

↓

Agent:
- reproduce
- identify affected service
- identify expected behavior
- define acceptance criteria

↓

Spec:

1. payment API must not return 500 for transient Redis timeout
2. retry twice
3. timeout <= 2s
4. add regression tests
```

最终形成：

```text
spec.md
acceptance.yaml
task.yaml
```

这一步非常重要，因为后面的 Agent 才能拥有“完成条件”。

---

# 3. Agent Workspace：每个任务独立工作空间

这是高度自动化的核心之一。

不要让多个 Agent 直接共用一个工作目录。

应该：

```text
                 Git Repository
                       │
              ┌────────┼─────────┐
              ↓        ↓         ↓
          Task A    Task B    Task C
          Sandbox   Sandbox   Sandbox
```

每个任务：

```text
Repository
   +
Worktree
   +
Environment
   +
Secrets Policy
   +
Tool Permissions
```

例如：

```text
/workspaces/TASK-1842/
    repo/
    logs/
    artifacts/
    test-results/
    agent-state.json
```

这样：

```text
Agent A 修改 auth
Agent B 修改 frontend
Agent C 修 bug
```

互不污染。

OpenAI 当前 Codex 的云端任务就是以独立 cloud environment / worktree 执行并支持多个任务并行，这已经成为现代 coding-agent infrastructure 的一个重要模式。([OpenAI][1])

# 4. Agent Harness：整个系统真正的核心

我认为这是你上一轮问题的延伸，也是整个架构最重要的部分。

```text
              Agent Harness
                   │
      ┌────────────┼────────────┐
      ↓            ↓            ↓
   Context       Tools        State
      ↓            ↓            ↓
   Memory       Sandbox      Planner
      ↓            ↓            ↓
      └────────────┼────────────┘
                   ↓
                LLM Router
```

Agent 不应该直接管理：

```text
files
git
shell
tests
browser
database
cloud
```

而应该：

```text
LLM
 ↓
Harness
 ↓
Capabilities
 ↓
Tools
```

Anthropic 最近关于 Claude Code 的工程分享也明确把 subagents、hooks、MCP、context strategy 作为长任务自动化的重要组成部分。([Anthropic][3])

# 5. Coding Pipeline：从单 Agent 变成流水线

推荐：

```text
                 TASK
                   │
                   ▼
             ┌───────────┐
             │  Explorer │
             └─────┬─────┘
                   ↓
             ┌───────────┐
             │  Planner  │
             └─────┬─────┘
                   ↓
             ┌───────────┐
             │ Implement │
             └─────┬─────┘
                   ↓
          ┌──────────────────┐
          │ Build / Test     │
          │ Lint / Typecheck │
          └────────┬─────────┘
                   ↓
               PASS ?
             /         \
           YES          NO
           ↓             ↓
        Review        Debugger
           ↓             ↓
          PR          Repair
                         ↓
                       Test
```

关键点是：

> “Test”不是 coding agent 的最后一步，而是 Agent 的反馈传感器。

# 9. Model Router：你的“类 MoE”放这里

结合你上一问，我会在生产流水线中专门放：

```text
                    MODEL ROUTER
                         │
        ┌────────────────┼─────────────────┐
        ↓                ↓                 ↓
    Cheap Model      Coding Model      Reasoning Model
        │                │                 │
   classifier         implementation     architecture
   summary            debugging          hard debugging
   extraction         refactoring        complex planning
```

更进一步：

```text
Task
 ↓
Difficulty Estimator
 ↓
Expected Value
 ↓
Model Router
```

例如：

```text
简单 bug
 → DeepSeek / Qwen / cheap model

普通 TypeScript feature
 → coding model

复杂架构
 → frontier reasoning model
```

失败才升级：

```text
Cheap
 ↓ fail
Medium
 ↓ fail
Strong
 ↓ fail
Multi-agent
 ↓ fail
Human
```

这比“所有任务 Claude Opus”高效得多。

# 10. Context Engineering 是生产流水线的隐形基础设施

真正高自动化以后，你最大的成本可能不是模型价格，而是 context。

所以：

```text
                Context Engine
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
    Repo Map       Memory         Task State
       ↓              ↓              ↓
    Symbol        Decisions        TODO
    Graph          Errors          Tests
       └──────────────┼──────────────┘
                      ↓
               Context Selector
                      ↓
                     LLM
```

特别不要：

```text
整个 repo → LLM
```

而是：

```text
Search
 ↓
Symbol
 ↓
Dependency
 ↓
Relevant files
 ↓
Relevant lines
```

另外 MCP 规模化以后尤其需要这种设计。Anthropic 已经公开指出，大量 MCP 工具会同时消耗 tool-definition context 和中间结果 context，因此“直接暴露全部工具”不是好的规模化方案，code execution / 动态工具发现会更省 token。([Anthropic][4])

# 11. 工具层：MCP + Native Tools + APIs

现代 Agent 工具层建议：

```text
                  Tool Gateway
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
     Native         MCP            REST/API
      Tools        Servers
        │              │              │
      git            DB             Jira
      shell          browser        Slack
      files          cloud          Linear
```

MCP 很适合作为统一协议层，但不要把：

```text
MCP
```

理解成“所有工具都必须 MCP”。

本地高频操作：

```text
filesystem
git
shell
grep
AST
test
```

通常直接 native tool 更简单、更快。

外部系统：

```text
GitHub
Linear
Slack
Jira
Sentry
AWS
GCP
数据库
```

MCP / API gateway 更合适。

# 12. Security：高度自动化以后必须成为独立平面

真正自动化后：

```text
Agent
 ↓
shell
 ↓
internet
 ↓
cloud
```

风险非常高。

因此建议：

```text
             Security Plane
                  │
      ┌───────────┼───────────┐
      ↓           ↓           ↓
   Sandbox      Policy      Secrets
      ↓           ↓           ↓
 container       OPA       Vault
      ↓           ↓           ↓
 network       approval     identity
```

核心原则：

```text
Low risk → automatic

Medium risk → policy

High risk → explicit approval
```

Anthropic 当前对 Claude Code Auto Mode 的设计已经采用了类似思路：通过风险分类自动处理部分权限决策，同时结合 sandbox 和更高风险操作的控制；OpenAI 也公开强调 coding agent 的 technical boundaries、approval 和 telemetry。([Anthropic][5])

# 17. 但有一个非常重要的反直觉结论

不要把系统做成：

```text
Agent
+
Multi-Agent
+
MCP
+
RAG
+
Vector DB
+
Graph DB
+
Kubernetes
+
Redis
+
Kafka
+
Temporal
+
...
```

然后以为这就高级。

真正成熟的软件工厂恰恰会不断把东西从 LLM 身上拿下来：

```text
LLM
负责：
    推理
    规划
    代码生成
    复杂诊断
    语义判断

传统软件：
    状态机
    调度
    搜索
    AST
    Git
    编译
    测试
    CI
    权限
    沙箱
    缓存
    日志
    指标
    部署
```

所以我会把核心架构总结成：

$$
\boxed{
AI\ Software\ Factory
=
Deterministic\ Infrastructure
+
Agent\ Harness
+
Model\ MoE
+
Automated\ Verification
+
Production\ Feedback
}
$$

而不是：

$$
AI\ Software\ Factory
=
LLM + MCP
$$

这也是为什么 2026 年真正值得关注的是 “Harness Engineering / Agent Orchestration / Cloud Sandboxing / Context Engineering / Verification”，而不是单纯 Prompt Engineering。Anthropic 已公开把长任务 harness、managed-agent infrastructure、sandboxing、observability、cost controls 作为独立工程问题；OpenAI 的 Codex/Symphony 也在往“长期运行的 agent + orchestration control plane”发展。([Anthropic][6])

对于你前面提到的“类 MoE、API 调用量最大”的方向，我最推荐的下一层是：把这个架构进一步收敛成一个“AI Software Factory OS”的实际工程目录、数据库 Schema、Agent State Schema、Model Router 算法、MCP/Tool Router、Docker Sandbox 和 CI/CD pipeline，让它达到可以直接交给 Claude Code/OpenClaw 开始实现的程度。
